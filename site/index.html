A browser for AI agents that fills forms and remembers.

Waymarker is a headless browser server for Claude Code, Codex, Cursor and any MCP client. It fills a whole form in one call, checks every value it wrote, and uses Qdrant to remember what worked, so the next visit is better than the first.

cargo install --git https://github.com/inamdarmihir/waymarker waymarker-cli
claude mcp add waymarker -- waymarker serve
v0.1, early. Tested end to end against real Chrome and a real Qdrant server. Evaluated on local fixtures built to reproduce known form-filling failures, not yet on the open web. This page says what we measured, how, and what we do not know.

The problem

Agents are slow and expensive on forms for two reasons, and neither is "the browser is slow".

One call per field

Typical tools make the model click, type, and re-read the page for each field. A 20-field form is 20+ turns, and every turn re-reads the whole conversation.

Forms are tricky

Dependent dropdowns that load asynchronously, wizards, input masks, controlled components that ignore a plain .value =, custom comboboxes, shadow DOM, iframes, silent validation.

Amnesia

Every session starts from zero: the same site quirks rediscovered, the same personal details asked for again, the same validation mistakes repeated.

How it works

Four calls cover most forms. The model states intent; the engine does the mechanics and reports what actually happened.

navigate  →  page state with interactive elements (no separate snapshot call)
form_inspect  →  typed fields: kind, label, required, options, current value, errors
                 + "this form was filled successfully 3x before; known issue: ZIP must be 5 digits"
form_fill {"Country":"Germany","State":"Bavaria","Date of birth":"March 5, 2001"}
  OK  e4 "Country" = "de"
  OK  e5 "State / region" = "by"          ← appeared after Country was set
  OK  e7 "Date of birth" = "2001-03-05"
form_submit  →  Submitted | Advanced (next step) | NOT SUBMITTED + the page's messages

Resolve

Keys match a field by ref, name, label or fuzzy label. If two fields match equally well, it asks instead of guessing.

Fill and verify

Fields are filled in document order, re-inspected after each (so dependent controls appear), then read back from the page.

Remember

After an accepted submit it stores the form's structure and which fact filled which field, in Qdrant. Never the values.

Engineering choices, and why

Each choice has a written decision record in the repo with the alternatives we rejected.

An injected runtime, not the accessibility tree

One script runs inside every page. It walks shadow DOM and same-origin iframes, assigns stable refs, and answers in one round-trip what would take dozens of protocol calls.

Why: fewer round-trips and one code path for shadow DOM. Cost: it shares a JS world with the page; closed shadow roots and cross-origin frames are invisible.

Wait for work, not for time

The runtime counts in-flight fetch/XHR and short timers and waits until the page is quiet and nothing is pending. No fixed sleeps.

Why: sleeps are either flaky or slow. Lesson: our own polling was counted as page activity and cost 3 s per action until a benchmark caught it. A regression test now guards it.

A form model, with read-back verification

Typed fields in, intent out. Typed input first (it fires real events); if the page rejects it, a native setter fallback. Page reformatting like (555) 123-4567 is reported as reformatted, not as an error.

Why: removes the round-trips and the silent failures. Cost: label matching must be trusted, so ambiguity is refused: 03/04/2024 is rejected.

Memory: most reliable signal first

Playbook mapping, then the field's autocomplete token matched by payload filter, then semantic search. Three Qdrant collections, one tenant filter, tenant-indexed with is_tenant.

Why: exact signals are cheaper and more trustworthy than similarity. Safety: secrets refused, sensitive fields never auto-filled, playbooks hold no values.

Observation is part of the action

Navigation returns the interactive elements; clicks and typing return only what changed. Tool schemas are capped at 7 KB by a test.

Why: saves a call per step and keeps context small. Every byte is re-read on every model turn.

Safety is structural

Domain allowlist enforced after redirects and clicks, optional human confirmation on submit, page text marked untrusted, background memory writes that never block a response.

Not claimed: an audit, or protection from a model that is persuaded by a page.

Economics, honestly

What an investor or senior engineer should ask first.

Compute is not the cost

~$0.006 per 1,000 tasks of browser compute versus ~$17–24 per 1,000 in LLM tokens. The product's value is fewer turns and fewer tokens, not a cheaper browser.

It scales on one node, with a known unknown

Near-linear to 8 sessions, flat latency. Qdrant retrieval is flat to 200k points, but Qdrant RAM per user (~130–160 KB untuned at 20 facts) needs a sizing study with quantization before any capacity claim.

The moat is not Rust

agent-browser is already a native Rust CLI with ~45k stars. What can compound is per-user memory, a corpus of form playbooks, and benchmarks others must match. Competitors can add memory; model vendors can ship first-party browsers.

The biggest gap

Real-site success rate. Until that evaluation is published, treat "reliable" as "reliable on the failure modes in our fixtures".

Limits and roadmap

Today it does not

Handle tabs or popups, cross-origin iframes, closed shadow roots, CAPTCHAs, 2FA, or calendar-click date pickers. It runs Chrome only, over stdio only, and is tested on macOS locally and Linux in CI.

Next

Real-site form evaluation with published failures · head-to-head benchmark · live Qdrant Cloud Inference validation · Qdrant sizing study · tabs and cross-origin frames · an optional Lightpanda backend if it earns its keep.
